# Linux Telemetry Matrix

Technical specification for the Linux sensor fabric (M2): every mechanism the
kernel/userland exposes, whether we use it, and why. Same discipline as
[`sources.md`](sources.md)'s own rule — an unused source is a **visible decision
with a reason**, never an unknown — applied at the level of detail Florian's
2026-09-21 telemetry survey asked for: hook, event, fields, MITRE coverage,
overhead, minimum kernel, required privilege, and how existing OSS EDRs
(Falco/Tetragon/Tracee/osquery/Wazuh) use the same mechanism.

Columns:
- **Overhead** — qualitative, this codebase's own experience where we have it
  (see each crate's doc for specifics), otherwise the general characteristic of
  the mechanism.
- **Min kernel** — the earliest mainline version the *mechanism* exists in, not
  necessarily what we require (`agent status` probes real capability at
  startup — BTF presence, verifier acceptance — never a hardcoded version
  number; see `crates/sensors/linux/userspace`'s own doc for why).
- **Required privilege** — as this codebase has actually observed it (several
  rows below note "confirmed empirically" in crate docs), not textbook capability
  lists — the two occasionally disagree (see sock_diag).

## Evaluated, not implemented

| Source | Verdict | Why |
| --- | --- | --- |
| Raw tracepoints (`raw_tracepoint/sys_enter`) | Rejected (revisit) | Generic per-syscall firehose; our tracepoint set already targets the syscalls that matter (`openat`, `connect`, exec/fork/exit) — no known gap this would close today. Revisit only if a specific syscall needs coverage no named tracepoint exposes. |
| Kprobes / kretprobes | Deliberately avoided | Every current hook is a stable tracepoint or an LSM hook precisely to dodge the kernel-function-signature fragility Florian's own note calls out (`Linux 5.x → 6.x, function signature changes, your sensor can break`) — matches this project's CO-RE/portability discipline (#53 lineage). Would only be justified for a kernel function with no tracepoint/LSM hook and no fentry/fexit alternative. |
| Fentry / Fexit | Not yet, likely next if a kprobe-class need appears | BPF-trampoline based, more stable than kprobes when the target kernel supports it (5.5+) — the fallback tier *above* kprobes, not tracepoints, if we ever need one. |
| fanotify | Evaluated, likely redundant today | Permission-mode file access control overlaps heavily with the BPF-LSM `file_open` hook's inline-block path (#91, blocked on the verdict model from #131/#133 either way) — a second, non-eBPF enforcement point for the same decision is duplicate machinery until there's a concrete gap fanotify closes that LSM doesn't (e.g., a kernel too old for BPF-LSM but new enough for fanotify's newer flags). Worth a real second look once #131/#133 land and the LSM inline-block path is exercised for real. |
| inotify | Rejected | Florian's own note agrees: prefer fanotify+eBPF over inotify as a primary source; inotify's per-watch model and lack of process attribution make it strictly worse than what we already have for the paths that matter (`sshd_config`, `sudoers`, `authorized_keys`). |
| PAM (uprobe on `libpam` or module) | Evaluated, journald covers the same ground for now | `pam_unix` session open/close already reaches us via the journald tail; a direct `pam_authenticate()`/`pam_open_session()` uprobe would be more real-time and authoritative (no reliance on the journal being configured to log PAM sessions) but is new attach-surface for a signal we already receive, degraded. Revisit if journald's PAM coverage proves to have gaps in the field. |
| Systemd unit lifecycle (as a `schema::Event`) | Parsed, not mapped — the actual #93 blocker | `sensor-linux-journal` already classifies `UnitStarted`/`Stopped`/`Failed` (see `classify.rs`) — there is no `schema::Event` variant to map it into yet. Inventing a Linux-only shape would preempt the same cross-platform decision `AuthEvent` needed (ADR-0005), and Windows' own service-lifecycle event semantics are still being reconciled against real captures (#224, blocking). Not a Linux gap — a shared-schema dependency on Windows. |
| Netfilter / nftables (rule-change visibility, NFLOG/NFQUEUE) | Not implemented | conntrack (in use) covers flow state; rule/policy-change visibility (someone modifying firewall rules — a T1562.004-style defense-evasion signal) is a real, distinct gap nothing above closes. Candidate for a future PR, not blocked on anything. |
| AF_PACKET / libpcap | Rejected | Full packet capture from the agent is the cost profile Florian's note also flags — TLS visibility is already covered more cheaply (and pre-encryption) by the uprobe path (issue #90) for the traffic that matters most. |
| XDP / TC eBPF | Not implemented, low priority | Network *defense* (DDoS filtering, inline drop) more than *detection* — out of scope until response/isolation (#25's host-isolation follow-up) needs an inline network-block primitive of its own. |
| Socket/cgroup BPF (attribution hooks) | Redundant today | The tracepoint `connect()` probe + `/proc` cgroup join already gets process/container attribution on a connection; a dedicated cgroup-BPF hook would matter more under heavy container density (many processes per cgroup racing the join window) — no evidence yet that our current join has a real race in practice. |
| SELinux AVC (`audit` record type 1400) | **Cheap win, not yet done** | The audit fallback sensor (#247) already subscribes to the *entire* `NETLINK_AUDIT` multicast stream — AVC denials are already arriving at the socket, `classify.rs` just doesn't have a match arm for `AUDIT_AVC` (1400) yet, everything not `EXECVE`/`SOCKADDR` falls into `_ => None` and is dropped. No new sensor, no new privilege, no new subscription — one classifier arm plus a schema field. Directly relevant to closing the SELinux-on-server blind spot (see "server distro gaps" below). |
| AppArmor (`audit` records via the same netlink stream, or `/var/log/kern.log` `apparmor="DENIED"` lines) | Not implemented | Same netlink stream as SELinux AVC in principle (AppArmor also logs through the audit subsystem on most distros), lower priority than SELinux specifically because none of our current lab boxes run AppArmor enforcing by default the way Rocky/RHEL run SELinux enforcing — no empirical validation target yet. |
| Seccomp (blocked-syscall events) | Not implemented | High value specifically for containerized workloads (most container runtimes apply a default seccomp profile) — sits closer to the Kubernetes/container-runtime XDR-adjacent scope than today's single-host EDR scope. |
| Linux capabilities (usage/changes) | **Changes: implemented; usage: not** | *Changes* ship as eBPF tracepoint events: `capset` (`Event::CapSet`, both capability words, #266/#457) and the capability-model options of `prctl(2)`, `PR_SET_SECUREBITS` and `PR_CAPBSET_DROP` (`Event::Prctl`, #457, filtered in-kernel). *Usage* ("this process just exercised `CAP_X`"): no dedicated kernel event stream outside audit rules configured for it (`-a always,exit -F arch=b64 -S capset` style) or BPF-LSM's `capable` hook specifically — candidate for a future BPF-LSM hook addition (cheap, same crate as `file_open`) rather than a new mechanism. |
| Docker Events API / containerd / CRI-O | Out of EDR scope, XDR-adjacent | Container *lifecycle* (create/start/stop/exec) rather than the *process activity inside* a container, which the eBPF sensor already sees regardless (host kernel, shared with containers). Matches `docs/sensors/linux.md`'s existing #80 scoping note: "deep container runtime security ... remain[s] explicitly out of scope until after v1." Revisit if Florian's XDR ambition formalizes. |
| Kubernetes Audit API | Out of EDR scope, XDR-adjacent | Orchestrator-level (who called the API), not host-level — a fleet/control-plane concern (M9-adjacent) more than a Linux sensor concern. Same "revisit under XDR" note as above. |
| ftrace / perf events / debugfs-tracefs directly | Rejected | eBPF already rides on top of most of this infrastructure (tracepoints are exposed *through* tracefs; perf-event-open is the eBPF attach mechanism for several hook types) — using them directly instead of through eBPF's verified, structured path gives up safety for no capability gain we've identified. |

## Server-distro gap this matrix surfaced

None of the mechanisms above are unavailable on server distros — the gap is
**validation coverage**, not missing code. `lab/MATRIX.md`'s two RPM-family rows
(`fedora-41`, `rocky-9`) are marked **replay-only**: they never actually attempt
live eBPF probe loading, only replay pre-captured telemetry through the detection
engines. Rocky's `generic/rocky9` Vagrant box ships **SELinux Enforcing by
default** (matching real production RHEL/Rocky), and there is documented
precedent (Red Hat, Carbon Black, Trend Micro) of confined-domain SELinux denying
`bpf()` operations — so whether our eBPF programs, BPF-LSM hook, and the new
audit-netlink socket actually load cleanly under SELinux Enforcing has never been
exercised, only assumed. See the SELinux AVC row above for the specific,
low-cost first step (classify what we already receive) before the bigger step
(provision a box with SELinux left in its real default, not disabled for dev
convenience, and see what — if anything — gets denied).
